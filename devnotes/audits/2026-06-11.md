[P1] SENTRY 100% TRACING + REPLAY + TUNNEL ROUTE              [HIGH]
  Files: instrumentation-client.ts:11-21, sentry.server.config.ts:11,
         sentry.edge.config.ts:12, next.config.ts:79
  Finding:
    - tracesSampleRate: 1 in all three runtimes — every page load and every
      function invocation generates a full trace.
    - Sentry.replayIntegration() loads the Session Replay bundle (~100KB+
      gzipped) on every page load and records 10% of all sessions.
    - tunnelRoute: "/monitoring" routes ALL browser telemetry through your
      own Vercel functions — extra invocations per page view (the config's
      own comment warns "this can increase your server load as well as your
      hosting bill").
  Impact: Largest single client-side JS cost on every public page; burns
    Sentry free-tier quota and Vercel function invocations.
  Recommendation (no functionality change — error capture unaffected):
    - tracesSampleRate: 0.1 (client) / 0.1–0.2 (server, edge)
    - Keep replaysOnErrorSampleRate: 1.0; consider replaysSessionSampleRate: 0
      (error replays still captured; replay bundle then lazy-loads on error)
    - Optional: remove tunnelRoute if ad-blocker loss is acceptable
  Effort: ~10 lines across 3 files.

[P2] TALKS LISTING: force-dynamic CANCELS ISR                 [HIGH]
  File: app/talks/page.tsx:12-13
  Finding: `export const dynamic = 'force-dynamic'` AND
    `export const revalidate = 3600` — force-dynamic wins, so /talks renders
    server-side on EVERY request. Compare app/cards/page.tsx and
    app/themes/page.tsx which use clean ISR (86400).
  Mitigating factor: getAllTalks is wrapped in unstable_cache, so the DB is
    not hit every time — but each visit is still a full function invocation
    + React render of the entire talks grid.
  History: comment says force-dynamic was added to "avoid DB timeout" at
    build time. That risk is now mitigated by the unstable_cache layer.
  Recommendation: remove the `dynamic = 'force-dynamic'` line, keep
    revalidate = 3600. Content freshness is identical (1h). If the build
    ever times out again, fall back to `generateStaticParams`-style
    on-demand rendering as done on detail pages.
  Effort: delete 2 lines, deploy, verify build succeeds and
    https://tarottalks.app/talks serves with x-vercel-cache HIT.

[P3] SPREAD-READING ROUTE MISSING maxDuration                 [HIGH]
  File: app/api/spreads/spread-reading/route.ts
  Finding: No `export const maxDuration` (13 other routes have one). The
    route makes 4+ sequential external calls (Gemini synthesis → YouTube
    search → Gemini talk selection → Gemini rationale → DB writes) against
    Vercel Hobby's 10s default timeout. This is the project's own
    documented gotcha #1 in devnotes/runbooks.
  Impact: Readings killed mid-flight under normal Gemini latency variance;
    user sees a failed reading after waiting.
  Recommendation: `export const maxDuration = 60;` (Hobby max). Pure
    config — protects existing functionality.
  Effort: 1 line.

[P4] DETAIL PAGES DOUBLE-QUERY THE DB PER RENDER              [MEDIUM]
  Files: app/cards/[slug]/page.tsx:24,68; app/talks/[slug]/page.tsx:23,69;
         lib/db/queries/cards.ts:39; lib/db/queries/talks.ts
  Finding: generateMetadata() and the page component each call
    getCardWithMappings(slug) / getTalkWithMappedCards(slug). Next.js dedupes
    fetch() but NOT direct DB calls — so every uncached render runs the
    query chain twice (getCardWithMappings itself is 2 sequential queries →
    4 DB roundtrips per card-page render).
  Recommendation: wrap the exported functions in React's cache():
      import { cache } from 'react';
      export const getCardWithMappings = cache(async (slug: string) => {...});
    Same for getTalkWithMappedCards. Per-request dedup, zero behavior change.
  Effort: ~4 lines across 2 files. ISR (86400/3600) limits blast radius,
    but this also halves load from og-image/twitter-image regenerations.

[P5] IMAGE OPTIMIZATION WRITES NOT CAPPED IN CONFIG           [MEDIUM]
  File: next.config.ts:5-21
  Context: You already hit an Image Optimization writes overage on Hobby
    (docs/my chat with Vercel support...txt) and deliberately use raw <img>
    in many components — do NOT convert those to next/image.
  Finding: For the places that DO use next/image (11 files, incl. card and
    talk detail pages), the config sets no minimumCacheTTL and default
    deviceSizes/imageSizes — Next re-optimizes more variants more often
    than needed for immutable deck art.
  Recommendation (config only):
      images: {
        formats: ['image/webp'],          // already good (no AVIF writes)
        minimumCacheTTL: 2678400,         // 31 days — deck art never changes
        deviceSizes: [384, 640, 828, 1080], // trim from 8 defaults
        imageSizes: [64, 128, 256],         // trim from 8 defaults
        ...
      }
    Fewer variants = fewer optimization writes AND better cache hit rate.
  Effort: 3 lines.
