# v1.7.0 - Admin Query Timeout Protection & Next.js 16 Compatibility 🛡️⚡

**Released:** Mar 11, 2026

## Summary
Fixed admin panel outage caused by query timeout starvation on the single-connection pool (`max: 1`), and resolved a Next.js 16 build-breaking change where `revalidateTag()` now requires a second argument.

---

## Features
- **Per-query timeout protection**: Added `withTimeout()` wrappers to all admin behavior and platform-usage queries — prevents any single hanging query (e.g., `pg_database_size` on pgbouncer) from taking down the entire route
- **Sequential query execution**: Changed `Promise.all` to sequential `await` in both `admin-behavior.ts` and `admin-platform-usage.ts` — on a `max: 1` connection pool, `Promise.all` caused timeout starvation where later queries in the queue had less and less time remaining on their shared timers
- **Graceful degradation for platform-usage**: If any individual query fails/hangs (8s timeout), `safeQuery` returns a fallback value and the route still returns data for the queries that succeeded
- **Next.js 16 `revalidateTag` fix**: Updated all 15 calls across 8 admin mutation routes to use the new 2-argument signature `revalidateTag(tag, 'max')` required by Next.js 16.1.6
- **behavior-debug `totalMs` bug fix**: Fixed incorrect elapsed time calculation that was subtracting a timing value instead of a start timestamp

---

## Root Cause Analysis

### The Timeout Starvation Problem
The connection pool is `max: 1` (correct for Supabase + Vercel serverless). When `Promise.all` submits 4 queries, they serialize through the single connection. But all 4 timeout clocks started simultaneously. If query 1 took 5s, query 2 only had 3s left on its 8s timer — and queries 3-4 had even less. They timed out waiting in the queue, not because they were slow.

### The `revalidateTag` Breaking Change
Next.js 16 changed `revalidateTag` to require a second argument (`'max'`). The v1.6.4 release had added these correctly, but a later version bump (likely the freshening in v1.6.9) reverted them to single-argument calls, causing a TypeScript compilation error.

### Diagnostic Process
1. Ran existing diagnostics script: 23/26 passing, behavior + platform-usage 504ing
2. Health check passed (247ms, DB fine, indexes present)
3. behavior-debug passed (all queries <100ms individually)
4. Vercel observability: 100% timeout rate on both routes
5. Root cause: shared timer starvation on `max: 1` pool + `revalidateTag` build error
